# 브랜치 완료 및 배포 절차

상시 승인·구현 규칙은 [AGENTS.md](../AGENTS.md)에 있다. 이 문서는 완료 작성물 또는 배포 검토 시에만 읽는다.

## 완료 작성물

1. 실제 `.github/ISSUE_TEMPLATE/`와 `.github/PULL_REQUEST_TEMPLATE.md`를 읽고 섹션·순서·체크박스를 유지한다. 기존 기록의 상세도도 참고한다.
2. Issue 작성안, 변경에 맞는 Conventional Commits 메시지, PR 작성안, Notion에 붙여넣을 Markdown 개발일지를 제공한다. 실제 Issue 번호를 확인한 경우에만 PR에 연결한다.
3. Issue·PR·개발일지는 개발자 관점의 `~했다/~한다` 평서형이다. 존댓말이나 “사용자가 작성”, “Codex가 구현”, “승인에 따라” 같은 불필요한 수행 주체 설명을 쓰지 않는다. 실행하지 않은 검증·Git·배포를 완료로 적지 않는다.
4. 예시 제목은 `[Feat] 이메일 인증 및 LOCAL 회원가입·로그인 API 구현`이다. 템플릿이 없다면 Issue는 작업 개요/To-Do/후속 작업, PR은 연관 이슈/작업 내용/테스트 및 검증/참고 사항 순서로 작성한다.

개발일지는 [기존 예시](references/개발일지 예시.md)의 상세도를 참고하며 다음 틀을 사용한다. 구현 배경·설계 이유·과정·검증 근거를 담고 단순 기능 목록으로 끝내지 않는다. 문제가 없었다면 문제 해결 절은 생략할 수 있다.

```markdown
# 작업 제목
- 작업일·브랜치·개발 환경·주요 기술

## 1. 작업 배경 및 목표
## 2. 주요 설계 및 구현
## 3. 구현 과정
## 4. 문제 발생 및 해결
## 5. 테스트 및 검증
## 6. 개발 결과 및 후속 작업
```

완료한 이전 브랜치의 작성물을 요청 없이 다시 작성하지 않는다. 작성안 제공 이후 실제 GitHub 작업은 별도 승인 사항이다.

## 프로젝트 문서 갱신

- CURRENT_STATUS: 현재 구현·검증·운영·한계·증거만 유지한다. 과거 단계의 “현재/다음/미커밋” 설명을 계속 덧붙이지 않는다.
- DEVELOPMENT_PLAN: 완료 단계와 다음 작업/순서를 갱신한다. 현재 상태·테스트 수·운영 로그는 복제하지 않고 CURRENT_STATUS를 참조한다.
- REQUIREMENTS/DATA_MODEL/AI_DESIGN: 승인된 요구사항·설계 변경이 있을 때 해당 문서에만 반영한다. 구현 상태를 반복하지 않는다.
- 과거 상세 증거는 `history/`에 날짜별로 보존한다. 스냅샷/manifest/원본 PDF/과거 작성물은 현재 지침으로 해석하거나 임의 재작성하지 않는다. 원본 수정 필요 시 위치·내용을 안내한다.
- 문서별 한 가지 책임을 유지한다. 새 공통 규칙은 AGENTS 또는 이 문서 한 곳에만 쓰고 다른 문서에서는 링크한다. 기존 Git 제외 정책은 유지한다.

다른 ChatGPT 대화로 이동을 요청받은 경우에만 인수인계 요약을 제공한다. 완료 브랜치/범위, 파일 경로/역할, 최종 필드/관계/Enum, Repository/조회 정책, Flyway/제약, 설계 변경/이유, 실제 검증, 미완성/영향, 다음에 읽을 코드/문서를 담는다. 영구 파일은 별도 요청이 있을 때만 만든다.

## 배포 준비 검토

실행 주체·승인은 AGENTS를 따른다. 코드/로컬 테스트 승인과 운영 승인을 분리한다. 검토 결과에는 다음을 포함한다.

- 대상 브랜치/커밋·포함 기능/변경 파일·로컬 검증
- Dockerfile/Compose·아키텍처·환경변수 이름·네트워크/외부 API 조건
- 운영 Flyway 현재 버전·신규 SQL·데이터 영향·백업/스냅샷·구버전 호환성
- Health/HTTPS/Swagger/OpenAPI·기존 인증·신규 API 정상/실패 시나리오
- 이전 이미지/Compose·DB 복구 절차·남는 데이터 변화·복구 한계

앱 시작이 Flyway 적용을 동반할 수 있다. 이미지 복귀로 DB/이월/Snapshot까지 복구되지는 않는다. 실제 로그/응답을 받은 뒤에만 운영 배포/검증을 기록하고 미확인 상태를 추정하지 않는다.

## OpenAPI 및 Swagger

- REST API 변경 시 실제 DTO·HTTP 상태·인증·오류 응답을 함께 갱신한다. 데이터 계층만 있는 기능을 실제 API로 문서화하지 않는다.
- Swagger는 기존 앱에 포함하여 운영 HTTPS에서 활성화한다. 별도 서버/컨테이너로 분리하지 않는다. 문서 공개와 API 인증은 독립이며 공개를 위해 JWT/소유권을 해제하지 않는다.
- 필요하면 Caddy Basic Auth/IP 제한 정책을 별도 검토한다. 쓰기 검증에는 테스트 계정/데이터를 사용한다. 실제 비밀값은 예시에 넣지 않는다.
- 배포 확인: Swagger UI·`/v3/api-docs` 정상, Security 경로·Bearer 인증·기존 인증/Health 유지, 테스트 계정의 인증 API 호출, 결과/설정 기록. 공개 문서 확인만으로 인증 API 성공을 완료 처리하지 않는다.
- 다른 도메인의 미완성 코드나 미적용 SQL을 Swagger 배포에 함께 섞지 않는다. Swagger 배포와 개별 API 완료를 구분한다.
